# 展示前檢查清單

## 上台前

- [ ] 開啟正式網址並重新整理一次，確認預設為「即時站況」。
- [ ] 確認 favicon、淺／深色模式、最小字級與 scrollbar 正常。
- [ ] 即時模式能顯示新北市站點、資料時間、地圖、待確認告警與待覆核任務。
- [ ] 從即時首頁進入「告警處理」與「調度建議」，確認模式、行政區及人工狀態都保留。
- [ ] 搜尋一個行政區或站名，點地圖站點後可看到可借車、可還位與基線判讀；滿位風險站要能看到 600m 內替代還車站或明確無可用站訊息。
- [ ] 按「歷史預測」，確認「回放時點」有情境名稱，並預先記住「晚間雙向供需壓力（04/26 17:00）」的位置。
- [ ] 在「晚間雙向供需壓力／60m」確認告警、補車與移車任務都有可展示資料。
- [ ] 按一筆告警的「確認」，確認只改變 Demo 狀態。
- [ ] 按「查看調度影響試算」，再按「指派補車」或「指派移車」，確認前後庫存與安全緩衝可讀。
- [ ] 重新整理後確認 Demo 的告警確認與任務指派狀態會重置。

## 三分鐘必講主線

1. 看到風險：新北官方即時站況、約五分鐘比對、30／60 分鐘歷史基線風險。
2. 收到告警：切到可重現的歷史情境，說明持續時間與人工「確認」。
3. 檢查調度：全域分配後的補車／移車建議、影響試算，再由人員「指派補車／指派移車」。
4. 量化效益：指出 60 分鐘保留測試 recall 44.5%，再以晚間情境 12 筆搬運、45 台車，將當下空滿站由 211 降至 198 的反事實試算說明可能效益。

## 必須誠實說明

- 即時模式會產生待確認告警與補車／移車建議，但只代表目前快照偵測，不會累積跨更新的持續分鐘；可重現持續時間以歷史回放展示。
- 歷史回放提供可重現的持續告警；即時與歷史的人工狀態都只在目前瀏覽器工作階段，網址會保留模式、時點與行政區。
- 風險值是啟發式指標，不是校準後的事件機率。
- 「確認」與「指派補車／指派移車」不會通知機關、保存案件或派出真實車隊。
- 效益卡量化保留測試與庫存反事實試算，仍不等於真實車隊已降低相同比例的空滿率或反應時間。
- 「整理摘要」是 template，不是生成式 AI。

## Q&A 準備

- 模型評估：60 分鐘保留測試 F1 39.2%、precision 35.0%、recall 44.5%；目前是可解釋基線。
- 歷史資料為何穩定：回放情境在 build 階段輸出成靜態 JSON，由 CDN 按需提供，避免 edge 處理大型資料而觸發 1102。
- 為什麼仍有 Function：新北來源的跨網域限制需要同源轉送；代理不解析、不儲存資料。
- 有沒有資料庫：沒有 KV、D1 或 R2；Demo 狀態只存在目前瀏覽器工作階段。
- 有沒有使用 Bedrock：公開 Demo 尚未呼叫 Bedrock；AWS AgentCore 已有受限的調度覆核整合設計，待活動帳號確認權限後再部署。
- 下一步：正式通知／案件保存、實際介入 KPI、道路與車隊限制，再以相同切分比較 LightGBM 等模型。

## 不要這樣說

- 不要說「即時模式已經會通知機關或自動派車」。
- 不要把歷史回放說成正在發生的即時事件。
- 不要把風險指標說成「有 86% 機率會無車」。
- 不要說「已證明降低空滿率」；目前只能展示預判與調度影響試算。
- 不要把 template 摘要、整合設計或未部署的 Bedrock adapter 當作目前 AI 成果。
