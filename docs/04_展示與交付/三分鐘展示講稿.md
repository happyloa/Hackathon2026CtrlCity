# 三分鐘展示講稿

正式網址：<https://hackathon2026ctrlcity.pages.dev>

展示前：開啟「調度中心」的「即時調度」模式；60 分鐘為預設判讀窗。歷史段落可選「晚間雙向供需壓力（04/26 17:00）」。

## 0:00–0:25｜痛點

「新北 YouBike 的難題，不是看見已經無車或無位，而是從全市站況中，提早找出下一個需要處理的站點。我們把即時庫存、歷史資料和調度建議，收斂成值班人員下一步可以覆核的任務。」

操作：指出資料時間、調度工作佇列與風險地圖。

## 0:25–1:10｜即時比對

「系統讀取新北市政府官方站況；資料更新後，會用同一站、同一目標時段的六個月歷史基線，比對目前庫存。點選風險站，就能直接看到現在的可借車／可還位、60 分鐘後的歷史基線與推估值。」

「所以它不是只告訴我們『有風險』，而是說明為什麼這一站應該優先補車或移車。未對照到唯一歷史站點時，系統只顯示即時庫存，不會虛構預判。」

操作：點一個地圖風險站，指出「現在／歷史基線／60 分鐘推估」。

## 1:10–1:55｜從風險到任務

「首頁先列搬運任務，再列待確認風險。每筆任務都有來源站、目的站、建議車數、距離與優先順序；展開後還能看調度前後的安全庫存。值班人員確認後才按指派，Demo 不會真的派出車隊。」

操作：展開第一筆任務的「調度影響試算」，再按「指派補車」或「指派移車」。

## 1:55–2:30｜歷史演練與證據

「切到歷史演練後，我們可以重現持續無車、無位與雙向調度情境。60 分鐘風險在 2026 年 6 月保留測試的 F1 是 39.2%，precision 35.0%，recall 44.5%。晚間壓力情境的反事實試算，12 筆可行搬運讓空滿站由 211 降到 198。」

「這是可重現的離線證據，不是宣稱真實車隊已達成同樣成效。」

操作：切換「歷史演練」，再展開「判讀依據與交班摘要」。

## 2:30–3:00｜結尾

「這個 Demo 已把新北官方即時站況、六個月歷史基線、無車無位風險與人工調度串成一條工作流程。它目前主張的是增進預判能力；下一步再接正式通知、調度紀錄與 AWS 競賽環境，驗證實際營運效果。」

## 被問到才補充

- 這是可解釋的歷史基線與風險排序，不是校準後的事件機率，也不是已部署的機器學習模型。
- 官方即時來源失敗時，切到「歷史演練」即可完成完整展示主線。
- 目前 Cloudflare 只作暫時展示；正式 AWS 帳號取得後才部署 S3／CloudFront、API Gateway／Lambda 與 AgentCore。
