# 即時歷史基線判讀流程

## 目的與範圍

本流程將主辦方提供的六個月新北市公共自行車歷史快照，轉成可在 Demo 中使用的「站點 × 時段」歷史基線；前端再將其與新北市官方即時站點庫存逐站比對，作為 **60 分鐘風險判讀與人工調度排序** 的依據。

它是可解釋的歷史基線，不是校準後的事件機率，也不是已訓練完成的機器學習模型。風險分數只能協助營運人員找出應優先確認的站點，不能取代現場判斷或自動派車。

## 資料來源與離線處理

1. 原始資料是主辦方提供、保留在本機 `docs/資料集/` 的六個月 CSV 歷史快照；該資料夾已被 Git 忽略，不會上傳到 repository、瀏覽器或目前的雲端展示環境。
2. 建置階段會驗證時間、庫存、容量與座標欄位，統一站名與行政區的比對鍵，並依預測目標時間歸入 **48 個半小時時槽**。
3. 每個「站點 × 目標半小時時槽」只保留壓縮後的統計摘要：樣本數、平均可借車、平均可還位、歷史空車／滿位風險與疑似服務異常率。原始列不會被帶入前端。
4. 歷史回放情境會只使用早於回放時間的資料建立基線，避免把未來觀測混入該情境的判讀。

> 目前時槽只區分站點與半小時，不另外切分平假日、天氣、活動或捷運事件；因此 Demo 不應說成「同星期幾的預測」。

## 即時匹配與 60 分鐘判讀

1. 即時模式經由同源、唯讀的 `/api/v1/live-stations` 取得新北市官方 Open Data 站點庫存；代理不解析或保存官方回應。
2. 系統以規格化後的「行政區＋站名」和歷史基線一對一匹配。名稱重複而無法唯一對照、沒有歷史樣本或站點非營運時，不產生歷史預判。
3. 以目前觀測時間加 **60 分鐘** 找出對應的目標半小時時槽，將官方目前可借車／可還位庫存與該站的歷史基線比較。
4. 預判庫存會同時參考目前庫存與歷史基線；若使用者已開著本頁面約 30 分鐘，才會額外納入這個頁面工作階段內的庫存變化。這不是跨頁、背景或長期追蹤資料。
5. 將目前庫存、歷史基線與 60 分鐘預判轉為風險分數、樣本狀態與待確認的補車／移車排序。

流程可簡化為：

```text
主辦方六個月 CSV
  → 離線站點 × 半小時基線（壓縮靜態檔）
  → 官方即時庫存（唯讀）
  → 唯一站點匹配 + 60 分鐘目標時槽
  → 目前／歷史基線／60 分鐘預判比較
  → 風險排序、待確認告警、人工調度建議
```

## 畫面比較輸出

選取已成功匹配的即時站點時，站點詳情會以同一個 60 分鐘目標時間呈現三組容易比較的數字，例如：

```text
現在：2 車／26 位
歷史基線（60 分鐘後，181 筆）：6 車／22 位
60 分鐘推估：4 車／24 位
判讀：可借車低於常態 4 台，列入補車優先排序
```

數字會隨官方即時資料更新而重新計算。畫面中的「風險分數 N／100」是排序用分數，不是「有 N% 機率會無車／滿位」的機率宣告。

## 樣本、匹配與使用限制

| 狀態 | 系統處理 | Demo 應如何解讀 |
| --- | --- | --- |
| 歷史樣本充足（至少 6 筆） | 顯示歷史基線與 60 分鐘預判。 | 可作為優先確認與排序依據，仍需人工覆核。 |
| 歷史樣本較少（1 至 5 筆） | 仍顯示基線，但明確標記樣本較少。 | 只作輔助參考，不宜單獨做重大調度決策。 |
| 未匹配、名稱重複或基線載入失敗 | 僅顯示即時庫存，不虛構歷史比較或預判。 | 請確認站名／資料來源；不要把它當成低風險。 |
| 非營運或疑似服務異常 | 不套用正常庫存風險判讀。 | 先確認站點服務狀態，再決定是否建立任務。 |

此版本尚未納入天氣、活動、捷運班次、真實調度紀錄或站點需求流量；模型評估數字與時間切分方法請以自動產生的[歷史風險基線評估](歷史風險基線評估.md)為準，不能延伸宣稱已改善真實營運 KPI。

## 人工覆核與調度邊界

- 告警與補車／移車清單是「待確認」建議；使用者必須先查看來源站、目的站、目前庫存、安全庫存與距離，再手動指派。
- 系統不會直接控制車隊、不會建立真實工單，也不會把瀏覽器內的確認狀態當成正式營運紀錄。
- 官方即時來源不可用時，系統不會以歷史資料冒充即時站況；展示可切換到明確標示的歷史演練情境。

## Demo 建議說法

> 「我們先讀取新北市官方即時站況。這一站現在是 2 車、26 位；系統將它和主辦方六個月歷史資料中，同一站、60 分鐘後目標時槽的基線比較。歷史基線是 6 車、22 位，綜合目前庫存後推估為 4 車、24 位，所以可借車比常態少 4 台，被排到補車待確認任務。這是可解釋的風險排序，不是宣稱 4 台或某個百分比一定會發生；調度員仍要確認附近供給站與現場狀態後才指派。」

## 部署與 AWS 現況

目前的 Cloudflare Pages 僅供團隊迭代與展示；本流程沒有在 AWS 建立 S3、Knowledge Base、AgentCore、Bedrock runtime 或其他資源。取得主辦方競賽帳號後，才會依 [AWS AgentCore 整合設計](AWS%20AgentCore整合設計.md) 將靜態前端與唯讀即時代理遷移至 AWS。AgentCore 的角色仍限定為調度說明／覆核助理，不負責產生或覆寫本文件的數值判讀。
