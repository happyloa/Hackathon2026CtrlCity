# YouBike 調度雷達：3 分鐘展示講稿

> 展示網址：<https://hackathon2026ctrlcity.pages.dev>
> 展示主軸：**看見現在 → 預判下一小時 → 人工覆核調度。**

這份講稿只描述目前實際可操作的功能。請把「即時站況」與「歷史預測」當成兩種不同資料模式：前者是新北市政府公開資料的當下庫存快照；後者才是利用歷史資料產生的風險判讀。

## 上台前 2 分鐘檢查

1. 用桌機瀏覽器開啟首頁「調度戰情室」，縮放維持 100%，讓左側導覽、控制列和地圖同時可見。
2. 預設停在「即時站況」，等待「官方資料時間」出現；若資料已載入，不需要為了展示而重複按「立即比對」。
3. 預先看一次「歷史預測」，維持「全部行政區」和 `60m`。目前資料產物的最新回放情境有告警與調度建議，適合作為固定展示路徑。
4. 若投影環境的深色模式仍不利閱讀，直接切到淺色模式；可讀性比展示主題切換更重要。
5. 不要承諾即時資料每次按鈕都會改變。畫面刻意只在官方資料時間或庫存真的變化時同步，以避免製造假的即時效果。

## 地圖怎麼解釋才不會讓人困惑

- 地圖是**新北市全域站點地圖**，不是台灣行政區地圖，也不是租借流向圖。
- 「即時站況」的圓點顏色代表**當下庫存狀態**：可借可還、無車可借、無位可還、暫停／異常。
- 「歷史預測」的圓點顏色代表**所選時間窗的未來風險等級**：低、中、高、需優先處理。
- 每次都先說清楚目前是「即時」還是「歷史預測」，再講顏色含義；不要把紅點說成模型保證會發生的事件。

## 備援處理

| 狀況 | 畫面處理 | 對評審的說法 |
| --- | --- | --- |
| 官方即時 API 暫時失敗，但已有上一筆資料 | 留在即時畫面，系統會保留最後成功快照並顯示提示。 | 「官方來源暫時無法回應；系統不會清空上一筆可用資料。為了展示預判流程，我切到可重現的歷史情境。」 |
| 官方即時 API 暫時失敗，且尚未有資料 | 直接切到「歷史預測」。 | 「即時來源不可用時，原型仍可用已驗證的歷史資料展示風險、告警與調度流程。」 |
| 按「立即比對」後數字沒有變 | 不要反覆重按。 | 「這正是設計重點：上游快照未變時不製造動畫或假更新，系統等待下一次官方資料變動。」 |
| 沒有顯眼的告警或建議 | 在「歷史預測」改選另一個回放時間，維持 `60m`。 | 「歷史模式可重播不同半小時情境；我選一個高風險時段來檢視完整處理流程。」 |
| 摘要產生失敗 | 繼續停在已顯示的事實卡。 | 「摘要層不可用不會影響告警或調度判讀；系統仍保留可追溯的數據事實。」 |

## 常見提問的誠實回答

### 模型準確率如何？

「目前是時間感知、可解釋的基線，不是宣稱可直接自動調度的最終模型。固定 217 站樣本以 1 至 4 月訓練、5 月選門檻、6 月保留測試；60 分鐘風險的 F1 是 39.2%、precision 是 35.0%、recall 是 44.5%。下一步會加入天氣、活動、捷運班次與實際調度紀錄，並做全站點滾動驗證。」

### 為什麼不讓 AI 自動派車？

「公共服務調度有安全、現場資源與責任歸屬。模型適合幫人員縮小注意範圍、整理當班重點；派車前仍需要人員確認來源站庫存與現場條件。」

### 你們有真的使用 Bedrock 嗎？

「程式已把 Bedrock `Converse` 的受限摘要介面和 AWS 部署邊界做好，但目前公開 Demo 預設使用可追溯的 template 摘要，沒有實際呼叫或驗證線上 Bedrock。取得競賽帳號、核准模型 ID 與預算後，才會把該 adapter 接上並進行驗證。」

### 即時資料與歷史資料各自扮演什麼角色？

「即時資料回答『現在要先看哪裡』；歷史模型回答『接下來一小時哪裡可能失衡』。兩者畫面與文字刻意分開，避免把現況誤讀成預測。」

## 一句收尾

「YouBike 調度雷達不是替人員派車，而是用可驗證的資料讓人員更早看見問題、更有依據地介入。」
