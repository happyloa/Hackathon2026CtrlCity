# YouBike 調度雷達：3 分鐘 Live Demo 腳本

## Demo 前 30 秒檢查

- 開啟首頁「調度戰情室」，確認已載入站點與地圖。
- 先使用「即時站況」；若官方來源暫時不可用，保留上一筆成功畫面並改切「歷史預測」繼續 Demo。
- 講解時清楚區分：**即時站況是官方庫存快照；歷史預測才是未來 30／60／120 分鐘的風險判讀。**

| 時間 | 畫面操作 | 建議講稿 |
| --- | --- | --- |
| 0:00–0:20 | 首頁、即時站況 | 「我們解決的是調度人員來不及看見空車、滿位問題。這裡同步新北市政府公開資料，讓值班人員先掌握此刻哪些站無車可借、無位可還或暫停。」 |
| 0:20–0:40 | 指出「官方資料時間」、每 5 分鐘比對提示；可按「立即比對」 | 「畫面依官方資料發布節奏每五分鐘比對一次。若站點庫存真的變動，才更新畫面並給同步提示；不是把舊資料偽裝成即時。」 |
| 0:40–1:00 | 點選紅／橘色站點 | 「站點卡直接呈現可借車、可還位、狀態與資料時間。即時模式不虛構未來預測，下一步切換歷史模式才討論風險。」 |
| 1:00–1:25 | 切換「歷史預測」，選早尖峰情境與 60 分鐘 | 「我們用六個月、約 1,332 萬筆站點快照，依站點、星期與半小時時槽建立可重現的庫存失衡風險。這裡看到的是 60 分鐘後的空車／滿位風險，不是租借量或 OD 流向的假設。」 |
| 1:25–1:45 | 點高風險站，展示原因、信心與歷史曲線 | 「每一筆判讀可回到歷史型態、當前庫存與容量安全門檻；車與空位同時為零會判為暫不可用，避免被重複當成空車和滿位。」 |
| 1:45–2:05 | 前往「告警中心」，確認一筆告警 | 「持續異常會獨立列為待處理告警。值班人員可以確認，系統保留人工介入，而不是自動派車。」 |
| 2:05–2:25 | 前往「調度工作台」，開啟一筆建議 | 「調度建議會配對不會跌破安全庫存的鄰近供給站，列出建議車數、距離與原因。這是可覆核的決策支援，不是替人員執行派車。」 |
| 2:25–2:45 | 回首頁按「產生本班簡報」 | 「AI 只把已驗證的事實卡與人工覆核中的調度建議整理成摘要；它不能自行編造站名、數字、原因或已完成的動作。」 |
| 2:45–3:00 | 架構圖／README 的 AWS 段落 | 「目前可用的是 Cloudflare Pages 上的 Nuxt Demo。AWS 的 S3、DynamoDB、Lambda 與 Bedrock 介面已做成可遷移骨架；Bedrock 尚未部署或驗證，因此不宣稱目前線上版已呼叫 Bedrock。」 |

## Demo 收尾句

「YouBike 調度雷達把『看見現在』、『預判下一小時』與『人工覆核後調度』放在同一個工作流，目標是降低空車／滿位、縮短發現到介入的時間。」

## 備援說法

- **即時 API 暫時失敗：**「官方來源暫時無法回應，系統保留最後一次成功資料；我改用可重現的歷史情境展示預測與調度流程。」
- **被問到模型準確率：**「目前是可重現的時間感知基線與風險原型。正式導入前，會以保留時段回測空車／滿位事件、校準門檻，再比較進階模型。」
- **被問到 AI 是否自動派車：**「不會。AI 僅處理受限事實摘要；派車建議和執行均須人工覆核。」
