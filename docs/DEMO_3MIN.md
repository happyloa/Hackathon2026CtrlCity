# 三分鐘展示講稿

正式網址：<https://hackathon2026ctrlcity.pages.dev>

## 0:00–0:25｜問題與範圍

「我們把範圍鎖定在新北市 YouBike。值班人員最需要的不是一張站點清單，而是知道哪些站即將無車、無位，還有先處理哪一筆調度。」

開啟首頁，指出「即時站況」與新北市地圖。

## 0:25–1:05｜即時站況

「這裡讀取新北市政府公開資料。因為來源的瀏覽器跨網域限制，我們只留一條同源、唯讀的輕量代理；它不存資料、不做分析，只把資料安全送到畫面。」

操作：

1. 用行政區或站名搜尋。
2. 點地圖站點，顯示站點詳情。
3. 指出紅色為無車風險、藍色為無位風險、灰色為疑似服務異常；圓點大小代表預估介入缺口。

「系統每五分鐘與官方更新節奏比對。來源資料真的變動時才有即時更新提示，不會為了動畫而假裝更新。30／60 分鐘呈現的是即時庫存結合同站歷史時段的啟發式風險指標，不是校準後的事件機率；未對照到唯一歷史站點時，系統只顯示即時庫存。」

## 1:05–1:55｜歷史風險與告警

切換到「歷史回放」。

「現在看到的是由歷史資料產製的情境，而不是把即時庫存假裝成預測。每個站都有 30、60、120 分鐘風險，並把持續無車、無位與疑似服務異常轉成需要處理的告警。」

操作：

1. 切換三個回放時間。
2. 點高風險站，說明趨勢與風險原因。
3. 點開告警，指出持續時間與風險分數。

「歷史情境是靜態 CDN 檔，使用者切換時才下載；因此不需要在 edge 上重算大型資料，也避免 Cloudflare 1102。」

## 1:55–2:35｜調度與人機分工

指出調度卡片與「查看調度影響試算」。

「每筆建議都列出補車或移車、來源站、目的站、建議車數、距離與優先度。影響試算同時顯示兩站的車位變化與安全緩衝，讓人員在接受前檢查建議是否合理。」

按下「接受調度」或「確認」：

「這是前端 Demo 的人工接受狀態，不會派出真實車隊，也不會永久保存。這個界線是刻意保留的：系統提供決策支援，最終仍由營運人員覆核。」

## 2:35–3:00｜AI 與成本界線

按下「產生交班摘要」。

「摘要只引用畫面上已驗證的事實，不自行發明數字。程式保留 Amazon Bedrock 的遷移介面，但線上 Demo 尚未呼叫 Bedrock，因此沒有額外 AI 成本或憑證風險。」

結尾：

「這個版本以 Pages 靜態歷史資產加上唯一的即時資料代理運作，沒有 KV、D1、R2 或付費 AI 資源；後續若進入正式營運，再把資料管線與人工核准流程接到後端。」

## 現場備援

- 官方即時來源暫時不可用：切到歷史回放，說明它是可重現的展示情境。
- 地圖圖磚較慢：先用行政區篩選、告警與調度卡片完成敘事。
- 被問到 AI：明確回答「目前是可追溯 template 摘要；Bedrock 是已準備、未部署的下一階段。」
