## 問題 1：三種「缺車」門檻並存

### 現象

首頁四個數字看起來互相矛盾（2026-09-12 13:35 線上資料，共 1606 站）：

| 畫面位置 | 程式判定 | 站數 |
|---|---|---|
| 首頁「目前空站」 | `currentState === 'empty_now'`，可借車 **恰為 0** | 104 |
| 地圖橘色「近端缺車」 | `availableBikes < NEAR_EMPTY_BIKES` = **< 2** | 180 |
| 缺車通報「即時 ≥30 分鐘」 | `availableBikes < lowBikesThreshold` = **< 3**，且持續 30 分 | ≈184 |

`< 3` 有 260 站、`< 2` 有 180 站 —— 中間那 80 站在清單裡算缺車、在地圖上卻不上色。

### 根因

`git log` 顯示這批常數分兩次進入專案，而 `NEAR_EMPTY_BIKES` 是唯一沒跟上的：

| commit | 常數 | 值 |
|---|---|---|
| `c222d0b` 調整地圖+全參數分離 | `NEAR_EMPTY_BIKES` | **2** ← 孤例 |
| `c222d0b` | `SAFETY_STOCK_POLICY.minimum` | 3 |
| `c222d0b` | `LOW_INVENTORY_POLICY.floor` | 3 |
| `64e9386` 更新進度 | `LIVE_SNAPSHOT_POLICY.lowBikesThreshold` | 3 |
| `64e9386` | `FROZEN_STATION_POLICY.stuckValueCeiling` | 3 |

**正確規則：可借車數低於 3 台（0、1、2 台）即為缺車。** 2 是漏改。

## 問題 2：站點狀態持續時間計到了正常狀態

### 現象

`5daa514` 把持續時間的來源從瀏覽器緩衝改為排程計算後，**1383 個 `normal` 站的 `stateMinutes >= 60`，最長 305 分鐘** —— 站點清單把「一切正常」顯示成「已持續 5 小時」。

### 根因

`aws/capture.ts` 的 `mergePersistence` 對**所有**狀態計時，`normal` 也算（這對它自己的用途是對的）。但 `useLiveDashboard` 無條件把 `stateMinutes` 當成 `statusDurationMinutes`，而這個欄位原本的契約是「異常已持續多久」：原始的 `stationStatusDurationMinutes()` 只在 `empty_now && bikes === 0` 或 `full_now && docks === 0` 時回傳數字，其餘一律 `null`。

`.scratch/dispatch-homepage-redesign/spec.md` 與 `issues/01-unify-severity-standard.md` 兩處已更正，並在文件開頭加上 `2026-09-12 更正` 註記說明改了什麼、為什麼：

| 位置 | 原本 | 更正為 |
|---|---|---|
| `spec.md`、`issues/01` 的嚴重度表與內文 | 可借車數 < 2 | < 3 |

同時移除了一句無法佐證的敘述：「此門檻在 ML 評估中明顯比完全缺車容易預測準確」。查證結果見下。

> **`ALERT_THRESHOLDS` 是對「完全缺車」調校的，不是近端缺車。**
> `scripts/evaluate-forecast.mjs:443` 的正樣本是 `target.currentState === 'empty'`，而 `'empty'` 在 `:155` 定義為 `availableBikes === 0`。`'low_bikes'` 這個狀態在 `:159` 有算出來，但不參與 precision/recall。也就是說那份評估從未比較過近端缺車門檻。
> 這不影響本次改動（沒有動 `ALERT_THRESHOLDS`），但文件的宣稱與實作不符，已移除。

### B. 名詞誤用：把「空站」叫成「缺車」 —— 已改文字（選項 1）

`app/pages/admin/roi.vue` 共 13 處標籤由「缺車」改為「空站」：指標卡、地圖指標切換、全日走勢、一週比較表頭、逐筆明細、以及 Precision/Recall 的說明文案。

**數字完全沒有變動** —— `emptyRate` 仍是 `emptyRate`。改的只是它的名字，讓它不再宣稱自己是「缺車率」。已經對外引用過的 3.67% 依然成立。

Precision/Recall 那四句文案也一併改了，理由同上：那份評估的正樣本就是 `availableBikes === 0`。

**刻意沒做的**（需要重跑資料，展示前風險太高）：

- 歷史剖面沒有符合「缺車」定義的欄位。只有 `empty`（`bikes === 0`）與 `lowBikes`（`bikes <= max(3, ceil(車格 × 0.1))`，**隨站點大小縮放**）。後者對 60 格大站是 ≤6，比缺車定義的 ≤2 寬四格，所以不能直接拿來替代。
- 要補正確欄位需重跑 `npm run data:profile`（`--max-old-space-size=12288`，1,304 萬筆觀測），並改 artifact schema 與 `useOperationalRoi.ts:68` 的位置式解構順序。
- `evaluate-operational-impact.mjs:17` 的失效定義同樣是 `=== 0`，是 ROI 改善率的分母。用 `=== 0` 其實是保守選擇（改善率不會因門檻放寬而虛胖），屬於評估方法取捨，不是 bug。

參考量級（1,304 萬筆觀測加權）：`emptyRate` 3.67%、`lowBikesRate` 20.64%，相差 5.63 倍。

## 部署

推送 `main` 由 `.github/workflows/deploy-aws.yml` 自動完成全部流程：`npm test` → `npm run typecheck` → 更新 API Lambda → **更新 capture Lambda** → `npm run aws:publish` → 等待 CloudFront 失效完成 → `npm run aws:smoke`。

### 哪些改動需要 Lambda 重新部署

用 esbuild 實際打包 `aws/capture.ts` 驗證，整個 Lambda 只含 4 個本專案檔案：

```
app/aws/capture.ts
app/aws/runtime-env.ts
app/shared/live-feed.ts
app/shared/parameters.mjs      ← 本次改動中唯一命中的
```

| Lambda | Handler | 需要重新部署 |
|---|---|---|
| `SnapshotCaptureFunction` | `aws/capture.captureHandler` | **要** —— 引用 `parameters.mjs` |
| `OperationsApiFunction` | `aws/handler.lambdaHandler` | 不用 —— import 樹未觸及任何改動檔案 |

`lowBikesMinutes` 是在 Lambda 裡算完才寫進 `state/persistence.json`，前端只讀不重算，所以門檻值住在部署好的那包程式裡 —— 只發佈前端不會改變它。

`parameters.mjs` **兩邊都要**：它同時被 Lambda 與前端引用（`operational-policy.mjs` → 地圖著色、`WarningPanel` → 文案）。只更新 Lambda 而沒重新發佈前端，地圖仍會用舊門檻著色。CI 兩者都做。

### 部署後的行為

門檻由 2 放寬到 3 **不會重置既有的計時**。`mergePersistence` 用的是：

```ts
const lowBikesSince = prior?.lowBikesSince ?? iso
```

放寬只會讓更多站開始計時，已在計時的站沿用原本的 `lowBikesSince`。新納入的 2 台車站點從部署當下起算，所以「即時缺車 ≥30 分」清單約 30 分鐘後才會反映完整結果。
