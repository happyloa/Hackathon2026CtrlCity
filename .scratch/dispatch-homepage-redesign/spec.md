# 首頁調度改版:統一嚴重度標準與地圖疊加渲染

Status: ready-for-agent

## Problem Statement

值班的調度人員打開首頁,看到的是一個資訊過載又互相矛盾的畫面。

同一個站點在三個地方會被說成三種嚴重度:示警清單依模型風險分數說它 `CRITICAL`、地圖依另一套規則上色、派遣清單又依營運優先分數把它排在後面。維修中的站點在示警清單裡是最紅的一筆,但派車過去根本無法處置。示警用的安全庫存是總車格的 10%,派遣路徑用的卻是 15%,所以會出現「示警說這站要補,但路線裡找不到它」。

畫面上還混著兩種觀眾的東西。模型的 F1、Precision、Recall 佔著首頁版面,那是給評審看的可信度證明;值班的人不會因為 F1 是 34.8% 還是 89% 而改變今天派車去哪。真正該一眼看到的「現在最急的是什麼」反而被擠到角落。

地圖本身也幫不上忙。它畫的是一顆顆獨立的站點圓點與公尺半徑的圓圈,看不出「哪一帶在燒」;而淺色底圖貼在深色介面上顯得刺眼。

## Solution

首頁只服務調度人員一種觀眾,並且讓全站對「嚴重度」只有一種說法。

**一套標準。** 嚴重度一律以**可借車數**判定,不再使用模型算出的風險等級。缺車的統一門檻是**近端缺車**(可借車數低於 2 台)——這也是 ML 評估中最容易預測準確的門檻。服務異常不再被歸類為「最嚴重的風險」,而是獨立狀態:它不參與嚴重度分級,也不進入派遣路徑,因為派車到場也無法處置。

**一張看得懂的地圖。** 地圖改為逐站畫柔邊色斑並以半透明疊加,重疊處自然融合,形成「一片綠底、有問題的地方透出紅色」的效果。綠色底層只畫一次,所以健康站密集的地區不會因為站多而看起來更嚴重。

**版面讓給行動。** 模型指標與預測來源切換移到營運 ROI 頁,首頁拿掉 KPI 卡列,改為:最上方一個示警下拉區(顯示未來 30/60 分鐘將缺車的站),下方左側是唯讀的建議派遣路徑摘要、右側是地圖。按下「立即調度」導向調度規劃頁執行。

**深色為預設,地圖恆為淺色。** 提供主題切換按鈕。

## User Stories

1. 作為調度人員,我想在首頁一眼看到現在最急的是什麼,這樣我不必自己從清單裡推敲該先做哪一件
2. 作為調度人員,我想讓地圖、示警清單、派遣路徑對同一個站說同一句話,這樣我不必猜哪一個才是對的
3. 作為調度人員,我想用「可借車數」判斷嚴重度,這樣我看到的數字直接對應民眾借不借得到車
4. 作為調度人員,我想讓維修中的站點以灰色顯示且不出現在派遣路徑裡,這樣我不會白跑一趟
5. 作為調度人員,我想在地圖上看出「哪一帶在燒」而不只是「哪一站在燒」,這樣我能規劃一趟涵蓋多站的路線
6. 作為調度人員,我想讓健康站密集的地區不要因為站多就顯得嚴重,這樣地圖的顏色反映的是問題而不是站點密度
7. 作為調度人員,我想讓孤立的空站即使周圍沒有其他站也看得見,這樣偏遠地區不會被忽略
8. 作為調度人員,我想看到「目前」「30 分鐘」「60 分鐘」三個視野的派遣路徑,這樣我能決定要不要順道處理即將發生的問題
9. 作為調度人員,我想讓較長的視野涵蓋較短視野的站點,這樣切到 60 分鐘時我不會漏掉現在就缺車的站
10. 作為調度人員,我想在切換視野時看到重新最佳化的路線,這樣路線仍然符合車輛容量限制而不是硬接幾站上去
11. 作為調度人員,我想知道每一站建議補幾台車,這樣我不必自己心算
12. 作為調度人員,我想讓大站的補車建議多於小站,這樣一個 60 格的大站不會只補 2 台
13. 作為調度人員,我想在示警區看到「即將」缺車的站,而不是已經缺車的站,這樣示警的意義是預警而不是重複已知的事
14. 作為調度人員,我想用下拉方式瀏覽示警清單,這樣我不必捲動整頁
15. 作為調度人員,我想在首頁只看到唯讀的路線摘要,這樣我不會在瀏覽時誤觸派發
16. 作為調度人員,我想按下「立即調度」後進入可編輯的調度規劃頁,這樣看與做的分界清楚
17. 作為調度人員,我想在首頁看不到模型的 F1 與精準度,這樣版面留給我真正要用的資訊
18. 作為調度人員,我想知道目前的預測來源是規則基線還是 XGBoost,這樣我能解釋自己為什麼派車去那裡
19. 作為調度人員,我想無法在首頁更改預測來源,這樣不會誤動到分析師的設定
20. 作為調度人員,我想在夜班時使用深色介面,這樣長時間盯著螢幕不刺眼
21. 作為調度人員,我想切換成淺色介面,這樣在明亮的辦公室也看得清楚
22. 作為調度人員,我想讓地圖底圖無論主題如何都維持淺色,這樣街道與地名始終清楚可辨
23. 作為調度人員,我想從左側 sidebar 在首頁、站點總覽、調度規劃之間切換,這樣導覽位置固定好找
24. 作為調度人員,我想點選地圖上的一塊區域就看到那一帶由哪幾站服務,這樣我知道要去哪幾個點
25. 作為調度人員,我想在示警清單點一筆就跳到地圖上的位置,這樣我能立刻理解它在哪
26. 作為調度人員,我想看到滿柱的站以不同顏色標示,這樣我知道那是要拖走而不是補車

28. 作為分析師,我想讓我的切換影響首頁的警示依據,這樣調度人員用到的是我認可的預測來源
29. 作為分析師,我想在營運 ROI 頁看到 F1、Precision、Recall,這樣我能判斷預測是否可信
30. 作為管理員,我想直接以網址進入 ROI 與營運調整頁,這樣在展示時我能檢查資料而不必在 sidebar 為它們留位置
31. 作為新接手的工程師,我想在詞彙表裡查到「缺車」「滿柱」「近端缺車」「帳面差額」的定義,這樣我不會誤用 `capacityGap` 去判斷缺車
32. 作為新接手的工程師,我想讓安全庫存只有一份實作,這樣示警與派遣不會因為門檻不同而給出矛盾的結果

## Implementation Decisions

### 接縫(共五個,全部沿用既有模組)

1. **`shared/operational-policy`** —— 營運政策的單一來源。新增嚴重度分級與補車量計算,並把安全庫存統一為單一實作。
2. **`shared/live-operations`** —— 警示與派遣的產生。示警清單需排除「目前已缺車」的站。
3. **`shared/risk-map-visuals`** —— 鄰近群計算。半徑 300m 改 500m,涵蓋範圍從「風險站」擴大到「所有營運中站點」。
4. **`shared/dispatch-route-planner`** —— 路線規劃。車輛容量 12 改 14。
5. **`scripts/build-artifacts`** —— 資料產製。停止把服務異常站的預測等級壓成最高風險。

### 嚴重度分級(新增於營運政策模組)

以**可借車數**與**可還車位**判定,六個互斥的級別。判定順序即為優先序:

| 級別 | 條件 | 顏色 | 調度人員該做什麼 |
|---|---|---|---|
| 服務異常 | 站點非營運中 | 灰 | 不處置,派車也沒用 |
| 滿柱 | 可還車位 = 0 | 天青藍 | 拖走 |
| 完全缺車 | 可借車數 = 0 | 紅 | 立刻補 |
| 近端缺車 | 可借車數 < 2 | 橘 | 排進本班 |
| 偏低 | 可借車數 < 總車格一半 | 黃 | 觀察 |
| 正常 | 其餘 | 綠 | 無 |

**服務異常優先於一切**:它一旦成立就不再看庫存數字,因為那些數字沒有意義。

### 缺車門檻與補車量分開

- **門檻**(何時該補)用**近端缺車**,即可借車數低於 2 台。此門檻在 ML 評估中明顯比「完全缺車」容易預測準確,是刻意選擇。
- **數量**(該補多少)用**安全庫存**,即補到 `max(2, 總車格 × 15%)`。門檻用絕對值是為了統一與可解釋,數量用比例是因為大站與小站的實際需求差很多。

這兩者刻意不同,不是疏漏。

### 安全庫存統一

目前有兩份實作:示警元件內嵌 10%,派遣政策用 15%。**統一為 15%,只保留營運政策模組中的那一份**,示警端改為呼叫它。這是目前示警與派遣結果不一致的直接原因。

### 服務異常與風險等級脫鉤

資料產製時目前會把非營運站的預測等級直接設為最高風險。移除此行為,讓服務異常成為獨立狀態。警示與派遣兩端本來就已各自排除非營運站,因此此變更不會使它們回流到派遣路徑;受影響的只有顯示層的等級標籤。

### 預測視野與三個分頁

- 分頁為 **目前 / 30 分鐘 / 60 分鐘**,語意是**累加**:30 分鐘涵蓋目前,60 分鐘涵蓋前兩者。
- **移除 120 分鐘**,包含其運算。搬運車一趟約 30–60 分鐘,120 分鐘的預測對當下派車沒有決策價值。
- 三個視野以**現有的單一視野函式呼叫三次**取得,不改其簽章。切換分頁時路線**整條重算**,因為車輛容量是硬限制,單純附加站點會產生不合法的路線。

### 示警區與派遣路徑的分工

- **示警區只收預測會缺車的站(30/60 分鐘),不收目前已缺車的站。** 已經發生的事不是預警,直接進派遣路徑。
- 示警區以下拉方式呈現,置於首頁最上方,同時顯示各視野的站數與空站/滿柱計數。
- 兩者使用**同一個近端缺車門檻**,差別只在時間點,不是兩套標準。

### 地圖渲染

**鄰近群不是著色單位。** 著色是逐站進行,重疊處靠半透明疊加自然融合,視覺上的「一塊」是浮現出來的。鄰近群計算仍然保留,但用途是回答「這一帶由哪幾站服務」,供點選展開使用。

渲染以**自繪 canvas 疊層**實作,而非地圖套件內建的圓點標記——需要控制繪製順序與透明度疊加,標記元件做不到。地圖套件僅負責底圖與座標轉換。

以下參數由原型驗證得出(四種畫法對照,見 Further Notes),它們比文字描述更精確:

```
半徑        500 公尺,依當前緯度與縮放層級換算為像素(非固定像素)
合成模式     source-over  ← 不是 lighter
底層        所有營運中站點,綠 rgb(34,197,94),peak alpha 0.10,只畫一次
上層        依序疊加,後畫者覆蓋先畫者:
              灰   0.22
              黃   0.20
              天青藍 0.36
              橘   0.36
              紅   0.36   ← 最後畫,永遠在最上面
漸層停點     0 → peak / 0.55 → peak×0.5 / 1 → 0
服務異常     不進底層(它不提供服務),只在上層以灰色出現
```

**綠色只在底層畫一次**是關鍵:若讓每個健康站各自疊一層綠,站點密集的地區會因為站多而顯得更嚴重,這與事實相反。

### 地圖套件維持不變

不更換地圖套件。原本考慮更換的三個理由——深色底圖、內建熱力圖層、明暗切換——在「地圖恆為淺色」與「自繪疊層」兩項決定之後都不再成立。免金鑰的淺色底圖現成可用,而免金鑰的深色底圖經查證並不存在。

### 頁面結構與導覽

- **左側 sidebar 三項**:首頁(調度)、站點總覽、調度規劃。
- **ROI 與營運調整保留路徑但不進 sidebar**,以網址進入,供管理員在展示時檢查。
- 模型指標與預測來源切換**只在營運 ROI 頁**。
- 首頁顯示**唯讀**的預測來源標記;選擇存於瀏覽器本機(本專案為靜態站台,無後端可存共用設定)。

### 首頁版面

```
[示警下拉區:30 分鐘 N 站 / 60 分鐘 N 站 / 空站·滿柱計數]
[建議派遣路徑(目前 / 30 分 / 60 分,唯讀,含「立即調度」)]  [地圖]
```

**移除 KPI 卡列。** 其中「需注意站點」與示警區的數字是同一件事的兩種數法,並存只會製造疑惑;「規劃路線數」在派遣路徑區塊本來就看得到;「空站/滿柱」併入示警區。

### 命名

「優先搬運清單」改稱**建議派遣路徑**。首頁的版本是唯讀摘要,完整可編輯的版本在調度規劃頁。

### 參數

車輛容量由 12 改為 **14**(依新聞實證:每車一次最多載運 14 輛)。

## Testing Decisions

### 什麼是好的測試

只測**外部行為**,不測實作細節。既有測試的命名方式已經示範了這個標準——例如「服務異常站會被呈現供檢視,但永遠不用於派車」描述的是行為與理由,不是函式怎麼寫的。沿用這個風格:測試名稱應該讀起來像一句關於系統行為的斷言。

本專案使用 Node 內建測試執行器與嚴格斷言模組,測試檔集中於單一目錄,以 `npm test` 執行。**不引入元件測試框架**。

### 要測的模組

| 模組 | 要測的行為 | 既有測試檔可沿用 |
|---|---|---|
| 營運政策 | 六個嚴重度級別的邊界值;服務異常優先於庫存判定;滿柱與完全缺車互斥;補車量補到安全庫存而非門檻 | 目前由營運操作的測試間接涵蓋,可新增專屬測試檔 |
| 營運操作 | 示警清單排除目前已缺車的站;三視野累加而非互斥;示警與派遣使用同一門檻 | 有(16 個行為測試,最主要的接縫) |
| 鄰近群計算 | 500m 連通性;涵蓋所有營運中站點而非僅風險站;輸入順序穩定;單站與無效座標不成群 | 有(3 個測試,含順序穩定性) |
| 路線規劃 | 車輛容量 14 的邊界;維修站不進路線 | 有 |
| 資料產製 | 服務異常站的預測等級不再被壓成最高風險 | 有 |

### 既有測試中需要一併修正的

改動安全庫存比例(10% → 15%)與車輛容量(12 → 14)會使若干既有測試的期望值失效。**這些是刻意的行為變更,應更新期望值而非放寬斷言。** 若某個測試在更新後失去意義,應改寫成描述新行為的測試,不可直接刪除。

### 不做自動化測試的部分

首頁版面、sidebar、主題切換、三個分頁的 UI、地圖疊層的視覺結果——這些沒有測試接縫,以人工驗收。地圖渲染的正確性已由原型以真實資料驗證過。

## Out of Scope

- **參數集中化**(將車輛容量、安全庫存比例、車隊規模等集中到單一設定檔)。已知需要,但整體完成並討論後再做。
- **車隊規模與派遣筆數上限的推導**。目前的派遣筆數上限沒有物理依據,應由車隊規模推導,但本次僅改車輛容量的值,不動這個結構。
- **調度規劃頁的內部樣貌**。本次只確定它是首頁「立即調度」的去處且可編輯派發,其版面留待該頁自己的票再談。
- **淺色主題的視覺設計**。本次確定深色為預設且提供切換,但淺色的實際配色沒有設計稿(既有的 21 張設計稿全為深色)。
- **XGBoost 的即時推論**。模型檔遠超靜態託管的單檔上限,目前為本機手動產生靜態快照,維持現狀。
- **警示頁的獨立存在**。警示併入首頁,不再是獨立頁面。
- **行政區邊界的分區著色**。已查證資料取得路徑,但本次的著色單位是站點而非行政區,該研究留作未來區級視圖的參考。
- **響應式與行動版**。既有設計稿全為桌面單一斷點,本次不處理。

## Further Notes

### 這份 spec 的依據

- **領域詞彙**見專案根目錄的詞彙表。本 spec 中的「缺車」「滿柱」「近端缺車」「安全庫存」「鄰近群」「預測視野」「服務異常」「帳面差額」皆依該處定義。**特別注意 `capacityGap` 這個欄位名指的是「帳面差額」(壞掉的車柱與維修中的車),是資料品質指標,不可用來判斷缺車嚴重度。**
- **地圖套件的選型查證**見研究文件目錄下的選型報告。
- **設計稿的盤點**見設計稿暫存目錄下的盤點表。
- **渲染參數的來源**是拋棄式原型(見下)。

### 原型

四種疊加畫法的對照原型已提交於獨立的 commit,可用 `git revert` 一次移除。其結論:

- **強度堆疊**(熱力圖套件的標準做法)畫的是**站點密度**而非缺車嚴重度,方向與需求相反,已排除。
- **全疊加**的綠色會互相疊深,健康但密集的地區看起來比實際嚴重,已排除。
- **兩層**只表達紅與橘,黃色與滿柱無法呈現,已排除。
- **勝出的是綠底加嚴重度疊加**,即上方渲染參數所述。

**清理時注意:原型的靜態資料檔位於公開資源目錄下,靜態產製會將它打包進正式站,移除原型時不可漏掉。**

### 實作順序建議

嚴重度分級與安全庫存統一應**最先做**,因為地圖、示警、派遣三者都依賴它。在它們統一之前改任何一端,都只是把不一致換個地方出現。
